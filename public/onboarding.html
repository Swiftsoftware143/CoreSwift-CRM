Setting up CoreSwift — the order that works

Every feature here is honest about what it needs: if something is missing, the screen says so and offers the control right there. This page is the same information in one place, in the order that avoids going back and forth.

The one rule: a feature that cannot work will tell you on its own screen, in a sentence, with the fix beside it. If you ever see an empty screen and no explanation, that is a defect — report it rather than hunting for a setting.

1. The account, before anything else

1Sign in and name the account. The account is the company; workspaces are rooms inside it. Nothing else depends on this, but every screen shows it.

2Invite one teammate. Not a formality: a workspace with a single admin cannot lose that admin (the delete route refuses the last one), and two people can test with each other.

3Create an API key. One active key per account, minted at signup; you will need it only if you connect an agent or another SwiftSoftware app. Guard it like a password.

2. The lists and tags everything else is built on

1Make the lists first. A list is a saved group of contacts — “Palm Bay Sponsors”, “Customers”, “Nurture”. Calendar capture, tickets, campaigns and automations all point at a list, so creating them first means you never have to leave a screen to create one mid-setup.

2Make the tags, in categories. Categories are how a set of tags is applied at once (“Products”, “Services”). For a lead temperature, create a category and switch on only one tag at a time: assigning Hot then removes Warm, so a contact is never two temperatures.

Why the order matters: a calendar that captures a sponsor needs a tag to apply and a list to join. If neither exists, the booking still happens — and writes nothing you can see.

3. Mail: the inbox needs an address before it can hold anything

Requires: a domain or subdomain you control, plus the DNS records the screen gives you. Until that exists the shared inbox can neither receive a reply nor send one.

1Add the domain on Email Domains and Sending. Copy each record it shows into your DNS provider — the two you cannot skip are the ownership record and DKIM, because without them mail is rejected or lands in spam.

2Create the mailbox — support@, billing@, whichever the public should reach. Each mailbox is its own address in the shared inbox.

3Decide what an inbound message does. Mail from a stranger creates a contact; attach the tags and the lists that contact should land on, per mailbox. Two public addresses usually need different lists, which is why the rule belongs to the mailbox and not to “email” as a whole.

Test it: send one message from an address you control. A contact should appear, carrying the tags, and sitting on the lists.

4. Tickets: a queue with no list has no funnel

Requires: a list for tickets to land on (create it here — the picker has “create a list” beside it), and inbound mail if customers should raise tickets by email.

1Choose the list tickets land on. Every ticket that arrives puts its person on that list, so “who has an open issue” is a list you can mail, not a screen you must open.

2Say what “closed” means. When a ticket is closed you can apply a tag, add the person to a list, take them off another, or send a message — configured once, applied every time.

3Per channel if you need it. Email, the chat widget and a form are different channels; each can put a person on a different list, so the follow-up matches how they reached you.

5. Calendars: what a booking writes to the CRM

Requires: a booking calendar with at least one position, opening hours, and — for capture — at least one tag, category or list selected. Otherwise the booking happens and writes nothing.

1Create the calendar and its positions, with prices and sizes. Set opening hours, or no time will be offered.

2Press “Edit capture settings”. Add the tags a booking should apply — they may contain {product}, {city} and {calendar}, filled from what the buyer chose — tick whole tag categories, and tick the lists the contact joins.

3Attach the checkout if the booking takes money, and say whether payment is taken inside the page before or after booking.

Test it: book from a phone with a real address. The Orders table shows a CRM column — “created”, or “none” with the reason. A test on a reserved address is deliberately not allowed to invent a customer, and it says so.

6. Automations, last — because they act on what exists

Requires: one trigger and one action. A rule with only a trigger never does anything; a rule pointing at a list that was deleted does nothing quietly.

1Start with one rule you will notice — “when a tag is applied, add them to this list” — and watch it fire before building ten.

2Use the same vocabulary everywhere: a rule is a field, an operator and a value. If the engine cannot run a pair, it refuses at save time rather than returning nobody.

3Every saved rule is a row you can correct. If you cannot see the rule on a screen, it is not saved.

7. The things people get wrong

  • Creating the thing after the feature. Make lists and tags first; every other screen points at them.
  • Testing with a test address. Reserved test addresses never create a customer. Test with an address you actually own.
  • Assuming an empty screen is broken. It should explain itself. If it does not, that is the defect.
  • Skipping DNS. A domain added but not verified sends nothing, and the screen says which record is missing — copy it exactly.
  • Two tags from one “temperature” category. Switch the category to one-at-a-time and the newest wins, in the database, whoever assigned it.
