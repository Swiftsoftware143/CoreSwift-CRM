CoreSwift CRM — Admin Guide

System Overview

CoreSwift CRM is the central CRM and automation platform. It manages contacts, deals, pipelines, campaigns, and email sequences with full template-based email delivery.

Quick Reference

  • Backend: Rust (Axum) @ port 8084, Docker container coreswiftcrm
  • Database: PostgreSQL — coreswift_crm database
  • Admin Web App: served by nginx on admin.coreswiftcrm.com
  • Repo: the CoreSwift-CRM source tree

Email Templates (New)

All transactional emails use database-stored templates in the email_templates table. Templates support {{variable}} placeholders for dynamic content.

Template Fields

  • name — human-readable label (e.g. "Welcome Email")
  • template_type — one of welcome, purchase_confirmed, password_reset
  • subject — email subject line (supports {{variable}} interpolation)
  • body — plain text body (supports {{variable}} interpolation)
  • html_body — HTML body (supports {{variable}} interpolation)
  • is_html — if true, uses html_body; otherwise plain body
  • is_default — if true, this template serves as the fallback for its type

How It Works

  1. When a flow triggers (e.g. forgot password, registration, billing), it calls send_template_email() with the template type and variable map
  2. The system looks up a matching DB template — tenant-specific first, then fallback to is_default = true
  3. If no DB template exists, a hardcoded inline template is used
  4. The rendered email is queued to outbound_messages for async delivery
  5. A background worker picks up queued messages and sends via SMTP

Admin UI

The admin interface includes a dedicated Email Templates page with:

  • List view showing all templates with type badges
  • Modal editor with subject, body, HTML body fields
  • Merge field menu button to insert {{variable}} placeholders
  • HTML/TEXT toggle between body modes
  • Create / Edit / Delete actions
  • Type filter to find specific templates

Default Templates (Seeded)

Three default templates are seeded on first migration:

  • Welcome Email — sent on account creation (includes credentials, next steps)
  • Purchase Confirmation — sent on successful payment receipt
  • Password Reset — sent with reset token and link

Calendar addresses: one per account, plus its own domain if it has one

Every account gets a working public calendar address the moment it exists: <account>.coreswiftcrm.com. Nothing has to be switched on, and no plan gates it — a brand-new account can open its own address and see its name on it straight away. The address shows that account’s active booking calendars, their slot types, how many places are left on each, and a booking form the visitor can send without an account.

Where the owner changes it: Calendar in the console, the card Your public calendar address. Two things are editable and one is not:

  • Calendar address name — the part before .coreswiftcrm.com. Letters, numbers and hyphens, 3 to 63 characters. The server refuses a name another account already holds (“already in use”), a name the platform reserves (app, admin, inbox, mail, api, calendar and the rest of the system's own hostnames), and anything that is not a legal DNS label. Uniqueness is enforced by the database, so two accounts can never share an address even if two people save at the same moment.
  • Use your own domain — the owner types the domain (for example calendar.yourbusiness.com), saves it, then creates one CNAME record pointing at the address the panel prints (<name>.coreswiftcrm.com) and presses Check now. The check asks the domain itself which account answers there: a domain that reaches this account is marked domain verified, and one that answers nothing, or answers for a different account, stays waiting for DNS with the reason printed underneath. A real visit to a correctly pointed domain marks it verified on its own, so the owner does not have to press anything twice.
  • The system address is never removed. Removing the custom domain (or never adding one) leaves the account answering at <name>.coreswiftcrm.com; a domain is an addition, not a replacement, so a mistake in DNS can never take a customer’s calendar away.

What the operator should know when a customer asks: the calendar page is served on a wildcard vhost for *.coreswiftcrm.com. The live named hosts (coreswiftcrm.com, www, app, admin, inbox) are matched first and are untouched, and the old pmail name now permanently redirects to inbox; an address that belongs to no account answers “No calendar at this address” and writes nothing. Only the account’s OWN active calendars appear — the account is resolved from the address the visitor called, never from a value in the URL, so one customer’s address cannot be made to show another’s calendar. A booking made on a hosted calendar lands in that account’s own bookings, with the same capacity rule, scoring event and round-robin hand-off as any other booking.

Plan note: the hosted page is part of the Calendar/Bookings module, so a plan that does not include bookings still shows the account’s name and address but no places to reserve.

Per-calendar addresses: each calendar is also its own page under the account address — <account-subdomain>.coreswiftcrm.com/<calendar-name> — and the owner can give one calendar its own subdomain, making the account the first path segment: <calendar-subdomain>.coreswiftcrm.com/<account>/<calendar-name>. Both names are checked server-side at creation, and a name another account or calendar already holds is refused with a plain sentence plus a suggested free name.

Verifying a whole account in one read

GET /api/booking/calendars/summary answers for every calendar on the account, in one call: its workspace, its public address and own domain, every position with price, compare-at price and how many dated slots are open, plus the saved tag rule and list rule. It also returns a problems list and a lines list — one readable sentence per calendar — so an operator can confirm ten city calendars without opening ten screens.

The problems are the checks a careful operator would make: a position with no price, a compare-at figure that is not higher than the price (so it would never show), a position with no open dates, a calendar with nothing bookable, a missing tag or list rule, a list rule pointing at a list whose name does not match the workspace, and a calendar with no public address. The same view is on the Booking screen as Check every calendar.

Entering a customer's account (impersonation) — and the two doors there are

Support sometimes needs to see exactly what a customer sees. There are now two doors, and which one you use depends on whose account it is:

  • Your own companies → Portfolio. Every portfolio company row carries an Open button that enters that company's own account. This is the door for your businesses, and it is the one that does not make you hunt.
  • Customers → Workspaces. The Workspaces screen is the customer list — one row per workspace with its owner, status, plan and created date. It deliberately leaves portfolio companies out, so the rows you scroll past are paying customers, not your own businesses; your companies live on Portfolio Companies. Probe/test workspaces are hidden until you tick Show probe workspaces. Select rows (or Select probes) and press Delete selected to retire them. Users is a separate screen: every person on the platform in one list with name, email, role and joined date, and a Send reset button on every real person's row.

Whichever door you use, pressing the button asks the server for a short-lived token scoped to that account (15 minutes), keeps your own session under a separate key, swaps the session, and raises a red banner naming the account — every screen below it belongs to the customer, not to you. The banner survives a page reload, so a refresh cannot leave you looking at customer data with nothing on screen saying whose.

Stop impersonating on the banner ends the session on the server, puts your own session back and returns you to your own account. Signing out also clears it, so the banner can never appear over the login screen. If the 15 minutes run out, reload and sign in again.

Portfolio companies: separate from customers, and what a Target does

A portfolio company is your own business, not a customer. It lives in CoreSwift exactly like a customer does — its own account, its own users, its own data — which is why it is tempting to list the two together. They are kept apart on purpose: with a hundred customers, or a thousand, a shared list turns finding one of your own companies into scrolling past every customer you have ever signed.

The Portfolio screen is where your companies live

  • Every row shows the company, its address, whether it is active, and how many people are in it. A company with nobody in it yet says so.
  • Open enters that company's own account (the red impersonation banner behaves exactly as it does for a customer).
  • Targets opens that company's own webhooks — the next section.
  • No account where Open should be means the company record exists but no CoreSwift account has been created for it yet. Add the account first; the button appears once there is something to open.

One trap worth knowing, because it is invisible on screen: a portfolio row carries two account references. One is your account — every portfolio company shares it, because you own them all. The other is the company's own account. The Open button uses the company's own; opening your own would look like a button that does nothing, since you would land back where you already were.

Targets: the webhook a portfolio company can have

A Target is one webhook address belonging to one portfolio company, so that company's own automation — n8n, Zapier, Make, Slack — is told when CoreSwift syncs it. It never hears about another company, including your other businesses.

  • What is sent, and when: a portfolio.synced event each time that company is created, or its name, web address, contact email, description or active state changes. The request carries the company, whether it was a create or an update, and the company's account id.
  • The key: if you give the Target an API key, it travels with every request so your automation can check the call really came from CoreSwift. It is stored sealed, and it is never shown back to you in full.
  • Events: leave it empty and the Target receives everything. Name specific events to narrow it.
  • Send a test delivers one test event immediately, through the same path a real sync takes, and tells you plainly whether your endpoint answered. Use it right after adding a Target — a Target you have never tested is a hope, not a connection.
  • Remove takes the Target away. Without it, an address typed wrong would live on your account forever.

This surface was, until 2026-11-21, a form that stored an address and an API key and sent nothing — nothing in the product read those rows. If you wired an automation before that date and never received anything, that was not your setup: there was nothing on the other end. Re-add the Target and press Send a test.

A word about two words: account and workspace

In this product an account is the customer (or one of your portfolio companies) — it owns the plan, the mail, the people and the data. A workspace is something inside an account. The screens, the buttons and the screens' own help text use the word account for the customer, and the top-bar switcher is labelled Account; if you ever see “workspace” where you expected “account”, treat it as a mistake worth reporting rather than a distinction to work out.

When nobody can pay: the dashboard says so

This app has no card checkout of its own — POST /billing/checkout/create and its provider webhooks were retired on 2026-09-25 and no payment provider exists in the integration catalogue. The only arm a buyer can be charged on is a plan's own hosted payment page (plans.checkout_url), which the upgrade screen offers as Open payment page. So the operator's Dashboard now asks whether any of those pages actually opens, and paints a red Buyers cannot pay card when none does — with the button that opens Plans & Billing.

That distinction is the point: on 2026-11-11 all four plan links on this install answered 404 to a real browser request (a real slug and an invented one answered identically), so every buyer who pressed Upgrade landed on “No Data Found.” while the catalogue looked sellable. A count of rows cannot see that.

The card is painted only from a read that succeeded and that found nothing to sell. A failed read paints nothing; a link whose host did not answer in time is reported as unknown, not dead, so a slow payment host can never be shown as a shut till; and the card clears only when every active paid plan carries a page that opened — one working page beside a missing or dead one still says Not every plan can be bought and names the plan, because the buyer picks the plan. The read is GET /api/billing/readiness (platform admins only, cached for five minutes): it lists the active paid plans, opens each plan's page separately, and probes up to six of them concurrently with a four-second bound, following up to three redirects. Its answer carries a verdict per plan (ok, no_link, not_https, dead or unknown) and the list of plans that block a sale. It refuses to fetch anything that is not https or that points at this machine or a private network.

Giving a plan a working payment page

This app has no card checkout of its own, so a plan is sold through the payment page you paste onto it. Four steps, about five minutes per plan:

  1. In your payment provider (Stripe, PayPal, or any service that makes a hosted payment page), create one payment link per plan you want to sell, for the amount shown against that plan in Plans & Billing.
  2. Open Plans & Billing in this console and find Plan payment links.
  3. Paste the link into that plan's box and press Save. It must start with https://.
  4. Leave Free empty: a free plan takes no money, so it needs no page.

Reload the Dashboard. The red card clears only when every paid plan's page opens — not when one does. Until then it names the plans that cannot be bought, and the Plan payment links panel shows, under each saved link, whether that page actually answered (the check is cached for five minutes, so reload after a few minutes). When a payment lands, switch the account onto the plan by hand on the Tenants screen — nothing in this app hears the provider's confirmation, so the money and the plan are two separate steps. The gap is no longer silent: pressing Open payment page files the buyer's plan request in the same queue as Request this plan, naming the plan, its price and the account, so the money that lands and the switch that must follow it meet in one place.

On 2026-11-11 the four links this install carried (https://mintbird.com/checkout/crm-swift-…) were removed. They pointed at a third-party site that answers “No Data Found.” to every address on it, so a buyer who pressed Open payment page reached nothing and nothing was charged. With no link, the upgrade screen offers only Request this plan, which reaches the operator — worse than a sale, but honest, and the Dashboard keeps saying so until a real link is pasted.

How Customers Pay

While no card checkout is connected, a paid plan is bought by asking: the customer presses Request this plan and a person switches the account on. Until this screen existed, nothing told that buyer where to send the money. Open How Customers Pay in the admin console (under Admin Settings) and write how you take payment in your own words — bank details, an invoice, any rail you use. The same words appear on the public pricing page (so a visitor sees them before signing up) and on the plan screen inside the app. Leave the box empty and every surface behaves exactly as it did before; saving an empty box switches the message off again, everywhere, at once. The text is capped at 4,000 characters, and only a platform administrator can read or change it.

API keys — more than one active key per account

An account's API keys are how the outside world reaches it: the sibling apps (FunnelSwift, WorkflowSwift, IncentiveSwift, ADASwift, MissedCall Respondr), an AI client through the MCP door, and an automation all present a key, and every key resolves to exactly one account. A workspace holds several active keys — one per capture app and one per AI client, each with its own name — so adding a key for a second purpose no longer replaces the key something else is already using. The ceiling is 10 active keys per workspace: an eleventh POST /api/personal-api-keys is refused with “This account already has 10 active API keys. Revoke one before minting another.” CoreSwift used to mint a separate key per sibling app (funnelswift (admin), workflowswift (admin), …); those were retired on 2026-11-13 and now answer 401. The direction is: CoreSwift holds each sibling app's own key (under its connection settings, to reach out to them), and each sibling uses a key issued by this account to reach in.

  • Every key has a role. A key is issued as read + write (workspace, the default) or read-only (read_only), chosen when it is created in the Integration Center or on the MCP page; any other value is refused, not defaulted. A read-only key reads everything its account can read and is refused every write, with a sentence and nothing written: the REST surface answers 403 this key is read-only — use a workspace key to write, and the MCP door answers this tool requires role `workspace`. The role belongs to the KEY, not the person — the same owner can hold a read + write key in the console and hand a tool a read-only one — and an operator's own read-only key is read-only on both doors too.
  • Copy does not render the secret. Copy posts the same session-only reveal the View button uses and writes the value straight to the clipboard — it never puts the key in a box, a modal or any other part of the page. So a screen-share or a shoulder behind the customer sees a toast, not a credential.
  • Rotation lives on ONE screen. View, Copy, Regenerate and Revoke all sit on the API Keys card in the Integration Center (the original location). The MCP page shows the account’s active keys at the TOP with View and Copy only: it carries no rotate/regenerate control and no rotate handler, and its prose points at the Integration Center for a replacement. This is a product rule, not a layout preference — a customer setting up an AI client cannot invalidate every other client with one stray press on the page they were told to paste a key on.
  • New accounts are minted with a key. Every account created through the signup writer (the public signup and the machine provisioning door) gets exactly ONE key in the same database transaction as the account row, labelled MCP — <account name>. If the key cannot be sealed, the whole account rolls back — there is no keyless account to repair later. Keys minted before this rule read auto-provisioned; they keep working and are not renamed.
  • Regenerate keeps the role. Regenerate (POST /api/personal-api-keys/:id/rotate) mints a fresh secret under the same name AND the same role, retiring the old one in the same transaction: the previous secret stops working immediately, and a read-only key can never come back as a read + write credential.
  • The cap is enforced on the mint. create_key counts the workspace's active keys before it mints and refuses at ten; revoking a key frees the slot. That replaced the old one-key-per-account unique index — migrations/207_multi_active_api_keys.sql drops it — which was a UI convention rather than a tenancy control, because every key already resolves to exactly one tenant_id.
  • Hash contract: key_hash = sha256_hex(plaintext), no salt, lowercase hex; key_prefix populated on every row; revoke clears is_active and keeps the row for the record, so a revoked key answers 401 because no active row matches.
  • The key stays viewable, and the view is recorded: the owner presses View on the API Keys card in the Integration Center (and on the MCP page, at the top) and the key appears in ONE CLICK — a valid console session is the whole credential (plan §6.2, David’s ruling of 2026-11-25: “a click to view”). An issued API key presented as the bearer is refused 403 on that route, so a read-only key can never use it to obtain a read+write secret. key_sealed is decrypted there and nowhere else, every reveal is written to personal_api_key_reveals (who, when, which prefix, from where), and MCP never selects it.
  • Nightly check: a scheduled report names any real (non-harness) account with no active key — report only, never auto-mint.

MCP — read-only AI access

The fleet MCP service answers at https://hooks.swiftsoftware.net/mcp and exposes named, read-only tools so an AI client (ChatGPT, Claude, Claude Code, Cursor, Hermes, or the customer’s own agent) can read an account's CoreSwift data. The MCP entry sits directly above Settings in the tenant console, and a key issued in the Integration Center is the token — choose the key’s role for what the client should be able to do (a read-only key is refused every write).

What the customer sees on that screen (rebuilt 2026-11-21 to match the reference layout): ChatGPT and Claude tabs with six numbered steps and a labelled ADDRESS row; the key card with View & copy; a Ready to connect block naming the account, with Test connection, Copy my setup and Advanced setup; example questions in three groups with a Copy on each row and a Don’t know what to ask? box that answers with ideas; an eight-group accordion of everything the AI can read; What it will not do; and a developer drawer with tabs for How it connects / Your API token / Claude Code / Claude Desktop / Codex / Cursor / Troubleshooting / FAQ.

Three deliberate differences from a typical vendor page, and do not “fix” them: the connection authenticates with the account's own API key because this app has no OAuth one-click flow; there is no list of connected apps because the key IS the connection (replacing the key on the API Keys screen disconnects everything, and the screen says so); and every example is a question because the service is read-only at the database, so promising “it can add a contact for you” would be a lie the product cannot back.

Read-only by construction: the server connects with the mcp_reader Postgres role (SELECT only) and exposes no write tool and no free-form SQL door. Tenant-scoped in SQL: every tool filters tenant_id = any(...) inside the query, so a token can only ever return its own account's rows. Coverage today: 46 entities / 138 generated tools plus six hand-written ones for this app, and the console's list of them is GENERATED from the service source (scripts/coreswift-mcp-entity-specs.py) so it cannot describe a smaller surface than we serve — a pre-push arm refuses a push that lets the two drift apart.

Message text is data. Any tool whose rows carry a message body says so in its own description: an agent that reads a customer sentence and follows it has been prompt-injected. The excerpt is capped in the select list so one long message cannot flood a client's context.

Industry Dashboards — one screen for the dashboards a account uses

Industry Dashboards in the console is where a account switches its industry dashboards on and off. Each one brings that business type’s own dashboard and automation templates: choose the ones that describe what the business actually does.

The plan decides how many. The screen prints the count in use and the ceiling in one line — for example “2 of 3 industry dashboards in use on Professional” — read from the account’s own plan, never a fixed number. When the count reaches the ceiling the remaining buttons are disabled and the screen says so; switch one off to make room for another. A plan that does not include industry dashboards says that plainly instead of offering buttons that cannot work.

Switching on writes the choice to the account straight away, so the dashboard is there the next time the person signs in. Switching off asks for confirmation first, and the count drops back by one — nothing else in the account is touched.

The same screen exists in the account console, so a customer can make the choice themselves; what an operator sees here is that account’s own selection, not a separate one.

Data mapping — teaching the CRM another app’s fields

CoreSwift is the last destination in the fleet: sibling apps push INTO it and nothing flows back up. Settings → Data mapping is the screen where an operator maps a source app’s fields onto this account’s contacts without code and without a per-app integration.

How it is built. The screen is three columns: the source fields it can read, the destination inputs (plain text plus {{data pills}}), and a live JSON preview of exactly what the writer would receive. Saving stores a mapping; nothing is written to a contact until an event arrives.

  • Source field discovery has no credential requirement on the sibling app. Every data point an app pushes is stamped with the sending app as it lands (contact_custom_fields.source_app), so the field list is a query over what has already arrived: the standard contact keys plus that app’s own delivered fields. The app’s own describe endpoint is tried first when a credential can read it (FUNNELSWIFT_SCHEMA_KEY etc., optional), and an observed list is used otherwise. Slug and stamp are compared ignoring hyphens and underscores, because an app slug and the stamp it leaves differ (multi-directory stamps multidirectory).
  • One writer. The runner calls external_api::upsert_contact — the same function the public POST /api/external/contacts endpoint uses. There is deliberately no second insert path: one dedupe rule, one place where tenancy is enforced.
  • Storage is integration_mappings (the mapping: source, destination, field_map templates, dedupe rule, options) and integration_mapping_runs (every attempt: status, refused fields, reason, resolved payload, milliseconds) — migration 155_data_mapping.sql.
  • Tenancy is inside every query (tenant_id = $1); a mapping cannot read or write another account, and the intake takes the tenant from the API key, never from the payload.
  • Idempotency is a unique index on (mapping_id, event_id): replaying the same event is recorded as a replayed no-op, never a second contact.
  • Destination fields are validated at save time against the contact writer’s own list, so a mapping that targets a field the writer cannot store is refused by name instead of failing at run time. metadata.<path> is the open-ended target — extra data never needs a migration. Company as a destination is greyed out with its reason; this milestone writes contacts.
  • Transforms are server-side and deterministic (no model in the path): trim, lower, upper, title, phone_e164, date_iso8601, bool, number, split_name, split_name:last, join, truncate(n), regex_extract(pattern), static.

The one destination rule that surprises people: on_match = create_new cannot create a second contact with an email that already exists. idx_contacts_tenant_email is unique and predates this feature, so the runner refuses and names the account’s own rule rather than inventing a row or silently downgrading to an update. update and skip behave as expected.

Endpoints (console routes are session-authenticated; the intake is authenticated by the account’s issued API key, added to route_policy::API_KEY_ROUTES):

Acceptance (all proven live, 13/13 on 2026-11-13, including that the harness leaves the account exactly as it found it): one lead creates one contact with list membership and metadata; a replay writes nothing; update / skip / create-new each behave as described; a missing required field is refused by name with no half-written contact; editing a template changes the resolved payload exactly as previewed; another account can neither read the mapping nor receive its data; and a target the writer cannot store is refused at save time.

Booking engine — one model, three calendar types

Booking is one engine, not three products. A calendar’s kind is chosen at creation and decides how openings exist:

kindopenings come frompriced
appointmentweekly availability rules, minus bookings and paddingper appointment
inventoryexplicit dated rows, each individually pricedper slot (per-weekday possible)
date_rangeany run of days with free capacityper day × days

Tables (migration 156_booking_engine.sql, additive): booking_calendars (already existed; gained kind, timezone, currency, hold_minutes, settings and a platform-wide unique slug), plus booking_resources, booking_availability_rules, booking_slots, booking_bundles, booking_orders, booking_bookings. Migration 158_booking_manage_token.sql adds booking_orders.manage_token: an opaque 64-character credential minted by the database, unique, and never derived from the row id.

Capacity and holds. A booking occupies capacity only while it is confirmed, or held and unexpired. Two buyers cannot take the same position: the check runs inside a transaction that locks the resource, and a hold that is abandoned expires on its own — there is nothing to clean up.

Money is integer cents throughout. Bundles (booking_bundles) are rules, and the single best applicable one is applied — they never stack, so a bulk price cannot accidentally go below what was intended.

Addresses. One calendar answers on three shapes, and the page reads whichever it is given: booking.coreswiftcrm.com/book/<name>, <account>.coreswiftcrm.com/b/<name>, and <own domain>/b/<name>. The /b/ folder is served by the calendar wildcard vhost (sites/calendar-coreswift.conf) as well as the booking vhost, so a account address carries every module in a folder — b for booking, i for the inbox — rather than one host per module. Resolution is by slug alone and slugs are unique platform-wide, so a link never depends on which address it was opened on.

A customer’s own domain needs three things in order, and only the first is theirs: a CNAME from their name to their account address; a certificate for that name on this origin (certbot is installed, and their DNS pointing here lets HTTP-01 complete against our own :80); and an nginx server block for the name serving book.html and proxying only /api/public/booking/. Nothing is issued for a domain that has not been verified as pointing here first, so no one can claim an address they do not control.

Surfaces. Operator routes live at /api/booking/* behind the app’s own auth middleware and a six-line adapter that turns the signed-in account into the engine’s tenant. Buyer routes live at /api/public/booking/* and every one of them is named in auth::route_policy::PUBLIC_ROUTES, so their anonymity is declared and measured rather than a side effect of a path. They are also reachable from booking.coreswiftcrm.com, whose nginx vhost proxies only the public booking API — a public address can never become a second door into the console.

An operator filling a position. POST /api/booking/calendars/:id/bookings takes a resource plus a slot_id (or a starts_at, or a start_date/end_date pair), a business name and email, an optional note, and confirm (default true — a booking taken on the phone is usually already agreed). It calls the SAME writer as a customer booking (create_order: capacity checked inside a transaction, resource row locked) and then confirms, so a hand-filled position is indistinguishable from a sold one and the buyer page shows it with no places left. A buyer pressing the same position afterwards is refused with 409. There is deliberately no second insert path.

Choice is limited by the owner, per calendar, in settings.limits: max_options (total), max_per_day, and max_advance_days (a horizon). All optional. They are applied INSIDE the availability builder and only when enforce_limits is true — the public route passes true, the operator's availability route passes false, because a hand-filled booking may need anything. Order is preserved, so the soonest positions survive the cap. A limit implemented in the page instead would be a suggestion: the public API would still hand out everything.

Why the limits exist (operator only — keep this reasoning out of customer-facing copy). The three caps are a demand strategy as much as a convenience, and the mechanism is worth writing down because it is easy to weaken by accident when tuning a page.

  • A cap manufactures visible scarcity. A wall of forty open dates signals that nothing is selling; five open positions signals that most are gone. The caps are applied AFTER ordering, so what a buyer sees is always the soonest handful — the shape of a calendar that is being taken.
  • A near horizon pulls decisions forward. max_advance_days stops a buyer parking a date three months out, where the booking is worth least (they can still change their mind, and the slot is frozen the whole time). A short horizon keeps demand landing in the next few weeks, which is the inventory that actually expires.
  • Keeping booked positions visible advertises the same thing. A position that stays on the page marked Booked is social proof; hiding sold positions makes the page look empty instead of full. That is why availability keeps them with remaining: 0 rather than dropping the row.
  • Both levers only work if they are real. If the caps ever hide positions that do not exist, the scarcity is a lie and a buyer who finds the truth stops believing the page. Never fake inventory or fake a booking to achieve the look.

Availability keeps sold positions in the list with remaining: 0 rather than dropping them — the page renders that as a Sold pill. Hiding them is a one-line change if an owner prefers it.

The manage link. /book/manage/<code> lets a customer reschedule, cancel or rebook without an account. The code in the URL is the credential and is scoped to one order; an unknown code answers 404 and reveals nothing. A move frees its own capacity inside the transaction first, so the capacity check judges the world as it would be after the move, and a refused move rolls back leaving the booking untouched.

Embedding. booking.coreswiftcrm.com/embed.js is served from the booking host, versioned with the page it drives. data-mode="inline" renders the calendar in the customer’s page (the frame reports its own height and stops at 1400px so a host page cannot grow unbounded); data-mode="popup" renders a floating button that opens the calendar in a modal. Both are iframes on purpose: the customer’s site never touches the booking or the card, and a change here cannot break their page.

Numbering. CoreSwift’s migrations/ is written by more than one lane. Two files with the same number make sqlx refuse to boot (“previously applied but has been modified”) — which took the app down once. Always take the next free number, checking both the repo and /opt/swift/docker/coreswiftcrm/migrations/, and never edit an applied file.

Affiliate Products & Commissions

CoreSwift does not push its plans to FunnelSwift. The commissionable product catalogue lives in FunnelSwift's affiliate_products table and is owned there — FunnelSwift's own plan-derived products, plus one platform-wide entry per sibling service (for example CoreSwift Free, source_app = 'coreswift'), each with its own price and commission rate. Nothing in this app writes to that table, so creating, renaming or deleting a plan here does not change the affiliate portal's catalogue. Products are managed in the FunnelSwift admin (Affiliate Products), which is the source of truth for what an affiliate can promote.

What CoreSwift does report is the commission trigger: when a tenant's subscription moves onto a paid plan, src/billing/handlers.rs posts the account owner's email, the plan name and its price to FunnelSwift, fire-and-forget inside a tokio::spawn so billing is never delayed:

FunnelSwift matches that email back to the affiliate lead, credits the commission against the product whose source_app is coreswift, and ignores a repeat of the same event id, so nothing is credited twice. Attribution is by the email address the referred business signed up with, and only a move onto a paid plan counts. See "Conversion Tracking" in the user guide for the full chain.

Environment variables: FUNNELSWIFT_URL (default http://localhost:8080) and INTERNAL_SYNC_KEY — the shared x-internal-key value the receiver checks. If FUNNELSWIFT_URL is empty, or the tenant has no owner email, the call is skipped and the rest of the app is unaffected.

CoreSwift carries no affiliate system of its own (kanban t_3d81b041): the duplicate local affiliate routes, the CRM-side profile / payout / product-board code, the plan flag that gated them and the hub actions that exposed them to integrator webhook tokens were all retired, so the FunnelSwift programme above is the only affiliate system in the fleet. The duplicate, orphaned schema went with them: migration 108_retire_dead_affiliate_schema.sql (applied 2026-10-02) dropped those tables from this app's database — none of them exists here any more, verified live with to_regclass(), and nothing in the app reads or writes them. The commissionable catalogue the paragraph above describes is FunnelSwift's, in FunnelSwift's database, and is untouched by this app.

Machine mail does not open a ticket. Inbound mail that is a server report (DMARC/TLS/ARF), a bounce (a random per-message sender, bounces@/postmaster@, a known bounce host), a no-reply or bulk-marketing mailbox, or promotional spam sent from an address imitating a desk (supportmount@) is stored in the Shared Inbox and deliberately opens no ticket — a queue is only worth reading when every row is a customer. The message is never lost: open it and press Turn into a ticket to promote it by hand. Rows that predated this rule were closed with a note, not deleted.

The mail screens a customer uses

The Shared Inbox tab of the console is where a customer reads their mail, and the Shared Inbox host (inbox.<their domain>) carries the same mail in a fuller client. Both read the same records, so a message a support call is about is in both places. The branded name is matched to the product that owns the domain before anything is served: one inbox.* front door covers the whole fleet, and a name that belongs to no app answers 404 instead of somebody else's screens (see The mail front door, and a customer's branded address in the ADASwift admin guide for how the map is built).

What the customer sees first. Signing in to the CRM lands on the Dashboard, not on their mail. Mail is two routes from there: the Shared Inbox tab lists every address with its status, message count and a LOG IN button that opens that one address in the mail client; and signing in at the mail client itself (inbox.<their-domain> or inbox.coreswiftcrm.com) opens Choose a mailbox — one card per address, each carrying the address and how many messages it holds, and the chosen address travels in the URL so a link can open one directly. So "I only see a list of addresses" on a support call is the chooser working, not a missing inbox; the address becomes a tick away, not a page they failed to reach.

The console screen offers: a rail of views (Inbox, Unread, Favorites, Drafts, Sent, Archive, Spam, Trash) each with a live count; an address picker (All, each created address, and Everything else / MISC for catch-all arrivals that match no mailbox row); a star that files a message under Favorites; and account-level labels with a name, a colour and a usage count, filtered server-side so the count and the rows cannot disagree.

The three-dot menu beside a folder carries Create subfolder, Mark all as read, Mark all as unread and Sort alphabetically (a client-side order over the page shown). Archive adds Move all to Inbox and Delete all messages, the second of which MOVES mail to Trash — it destroys nothing. Spam and Trash add Empty folder, which names the exact number of messages before it destroys them.

Deleting one message from Spam or Trash destroys it immediately and never moves it to Trash, because those two folders are the last stop. Mail deleted anywhere else moves to Trash first. If a customer says mail vanished, check whether they emptied Spam or Trash: nothing in the app can restore from either.

Summarise appears on an open message only when the account has an AI provider key, and a provider failure is shown in that same spot as the provider’s own sentence rather than a silent no-op.

Setting Limits (PATCH /api/v1/private-email/admin/limits/:tenant_id)

{

  "max_mailboxes": 50,

}

Rules:

  • Set a number to override the plan default with your value
  • Set null (or omit the field entirely) to fall back to what the tenant's plan provides

Field meanings:

  • overrides — the full override row you've set for this tenant (null if no overrides exist)
  • effective_* — what's actually enforced: your override wins if set, otherwise the plan default
  • sells_catch_all — whether the tenant's current plan includes catch-all (the entitlement the inbound receiver asks at delivery time)
  • catch_all_domains_enabled — how many of this account's domains still carry the remembered catch-all switch
  • catch_all_domains_off_plan — how many of those are refused right now because the current plan does not sell catch-all (non-zero is the ordinary residue of a downgrade; see "Catch-all is part of the plan" below)

Listing All Overrides (GET /api/v1/private-email/admin/limits)

Returns an array of all tenant_email_limits rows, sorted by newest first. Only returns tenants that have at least one override set.

How Enforcement Works

When a tenant tries to add a domain or create a mailbox, the system checks in this order:

  1. Admin override first — looks up the tenant_email_limits table for a row matching the tenant
  2. Plan defaults fallback — if no override exists for a given field (or it's null), the tenant's plan features JSON is used
  3. Hard block on limit — if the tenant has hit the effective limit, they receive a clear error message:
  • Domain limit: "Domain limit reached (X/Y)"
  • Mailbox limit: "Mailbox limit reached (X/Y)"
  1. Feature disabled — if private_email: false in the plan features, the tenant gets "Private Email not available on your plan" for any operation

Catch-all is part of the plan, not the domain

Catch-all — accepting mail for any address on a account's domain that nobody created — is sold by the plan: Professional, Agency and Enterprise carry it, Free and Starter do not. The switch on a domain row is the account's preference; the plan is the entitlement. The inbound receiver asks the plan every time a delivery needs it, so these two facts are both true and are reported separately:

  • A account that enabled catch-all and is then moved to a plan that does not sell it keeps the switch remembered, and every mail to an unknown address on that domain is refused — no message row, no contact, no ticket. Nothing has to be cleared by hand, and a later upgrade restores the behaviour with no action from the customer.
  • The domain list (GET /api/private-email/domains) reports the stored switch as catch_all_enabled, what the receiver actually does as catch_all_effective, and catch_all_off_plan plus a catch_all_hint sentence when the two differ. The customer console paints "off — not on your plan" in that state, never "on".
  • The admin email-limits report (GET /api/private-email/admin/limits/:tenant_id) carries sells_catch_all, catch_all_domains_enabled and catch_all_domains_off_plan; the limits table on this console shows those as its Catch-all column, so a account whose stored switch is being refused is visible instead of inferred.

Removing Overrides

To remove an override and let a tenant revert to their plan defaults, PATCH with null for all fields:

{
  "max_domains": null,
  "max_mailboxes": null,
  "max_aliases_per_mailbox": null
}

The override row remains but all fields are null, meaning the plan defaults apply for every limit.

Sync New Company — giving a company its own account

Where: Admin console → Portfolio Companies → 🔄 Sync New Company. This is the one press that turns a business into a real account with a real login — either a brand-new client, or a portfolio record that never had an account behind it.

A mirrored company is permanent: the account console, the admin panel’s Delete selected control and the fleet’s own deprovisioning door all refuse to remove an account the Portfolio Companies registry names. That registry is what the delete guard reads — not a list of names in the code — so a company synced tomorrow is protected the moment it appears, and the account’s is_portfolio flag is set by the same sync so the two never disagree.

What one press does

  1. creates the company’s account and puts it on a plan — the entry plan, or the tier picked in the dialog;
  2. creates its owner login with role = owner, the same role a self-serve signup gets, so the owner can invite people, open Settings and manage the account;
  3. writes the portfolio entry — or converts the record that is already there — and stores the account’s id on it (settings.account_tenant_id), so the row always names the account it belongs to and the company stays in the operator’s portfolio list;
  4. emails the login details and the password to the owner address: the same welcome mail a signup receives.

The dialog says afterwards which of those happened. An account that was created with a mailed password reports that the mail went out; an account whose mail failed says so plainly rather than promising an inbox that stays empty.

Running it again

A company that already has an account answers already exists: its name, contact address and description are refreshed and nothing else happens — no second account, no second login, no second email. Two presses cannot make two accounts.

A record created with + Add Company is a plain record, not an account. Pressing Sync on it converts it: the account and the owner login are created and the record gains the account link. The same press on a company that is already converted never mints a second account.

If the email does not go out

The account still exists and the row is marked as having a password nobody has seen. The owner can set their own first password with Forgot password? on the sign-in page, or use the reset link they receive. Pressing Sync again does not re-issue an existing account’s password — for a mail problem, Forgot password? is the door.

What is refused, and why

  • An address that already signs in to a account on CoreSwift — one person belongs to one account at a time. Use a different owner address.
  • A plan that is not on sale (no working payment page). The refusal names the plan and nothing is created.
  • A plan slug that does not exist — likewise named, nothing created.

Accounts (per account)

An account is a business; a account lives inside it and holds the work (contacts, companies, mail, calendars, pipelines, automations), while settings, plan, branding and team members stay at the account. Every account gets a default account named My Account at creation — the signup writer mints it, and an AFTER INSERT trigger on tenants (migration 134) plus a backfill (migration 133) close the gap for any account minted another way, so nothing ever lands blank.

The customer manages accounts from the 🗂️ menu in the top bar, next to the plan badge — never the side menu. It offers switch (POST /api/accounts/<id>/switch re-mints the session with wsid set, reusing the login token-mint path), add, rename, make default and delete over GET|POST /api/accounts, PATCH|DELETE /api/accounts/<id> and POST /api/accounts/<id>/default, all scoped to the caller’s own claims.aid.

Rules the server enforces: a name is unique per account (case-insensitive, 120 characters); the first account becomes the default; exactly one default per account at all times (checking one moves the flag, and with one account it cannot be unchecked); deleting the default promotes the oldest remaining one; an account can never drop below one account; the account the caller is signed into cannot be deleted; and a portfolio business — one named in the Portfolio Companies registry, one whose name or slug carries an owner marker, or one flagged is_portfolio — can never have a account deleted. A plan declaring max_accounts in plans.features refuses further creations with the plan-upgrade sentence (none declares it today). Roles: a member sees switch and add only; rename, delete and make-default are owner/admin only (is_account_admin or an impersonation session).

The two-level switcher: the same top-bar menu lets a platform operator switch business — the existing impersonation door (POST /api/admin/impersonate, platform admin only) mints a 15-minute token for the chosen tenant, and the account menu then switches between that business’s accounts.

Your profile picture

Any signed-in user can add a picture from their own profile screen: the file picker under Profile picture takes the file and uploads it immediately. Once set, the picture is shown in the console header and on the account's own profile; with none set the header shows the account's initial.

Changing a sign-in email address

A customer can now move their own sign-in address with no support ticket: Profile in their account → Sign-in email → type the new address and press Send confirmation link. The app emails a confirmation link to the new address, and that address only becomes the sign-in identity when the link is opened — so a typo cannot lock anyone out, the old address keeps working, and nothing at all changes if the mail is never opened. The link works once and expires in two hours.

This console's own Profile screen carries the same card, for your account. There is deliberately no screen for moving a customer's address from here: point them at their own Profile, and if they cannot sign in at all, use Impersonate on the Tenants screen and do it from the customer's own Profile — the app still mails the confirmation link to the new address, and only whoever controls that mailbox can confirm it.

Routes: POST /api/auth/email-change (authenticated; acts on the session's own row, writes one pending row and queues the confirmation mail) and POST /api/auth/email-change/confirm (anonymous by necessity — the token in the link is the credential and is redeemed once). The mailed link lands on /confirm-email-change, which the app vhost serves from its own page. Pending requests live in the email_changes table. A reserved test address (the RFC-2606 names and the fleet's own harness domains) is refused before any row is written, because the mailer suppresses those destinations — so a mistyped test address can never retire a real pending request.

A customer closing their own account

Every account can leave without a support ticket: the last card on a customer's Profile screen is Close my account. It asks for their password and the word CLOSE, and only then posts POST /api/auth/close-account (the fleet path /api/v1/auth/close-account answers the same handler). Nothing is deleted: the row keeps a closed_at timestamp, so you still see the account, its contacts, deals and history in every operator read.

What a closure ends: every token minted before it (the account's session line, users.sessions_valid_from, is moved one second past the moment of the close), every live API key on the account (the rows are kept and marked inactive, so the record is auditable), and every way back in — sign-in answers 403 with the closed sentence, refresh answers 401, forgot-password sends no link, and reset-password refuses even a token minted before the closure.

Both consoles carry the card (2026-11-19). The customer SPA has had it since the route shipped; this admin console showed nothing on its own Profile screen even though the route was already mounted there, so a customer who signs in at the admin host had to open a support ticket to leave. The card sits at the bottom of Profile and is hidden while you are impersonating — the route acts on the caller, so in someone else's account the button would close their account. A platform operator account is still refused by the server with its own sentence, shown in the console: an operator closes accounts, and losing its own login would take the console away from the person who runs the install.

Reopening is an operator decision, not a button: clear users.closed_at for the account (and mark its API key active again if the customer needs it). Their password still works and their data never moved.

Private Email — the free inbox (30-day trial) and the Inbox line (not on sale yet)

Every Free account may create one mailbox on their own domain with their own Mailgun account (bring-your-own-key). It is fully working — send and receive — for 30 days. When the window closes the mailbox does not stop: it drops to receive-only. Mail keeps arriving, nothing is deleted, and the address keeps working. Sending is what needs a paid plan.

The 30-day clock starts when the first mailbox is created on a verified domain, never at signup. A customer waiting on DNS loses nothing. There is no CoreSwift-hosted trial address: no free customer's mail passes through our domain or our Mailgun account.

The Shared Inbox tab is the setup: add the domain plus that customer's own Mailgun API key and webhook signing key, add the records the page lists (each with a Copy button, one sentence saying what it does and a live Active / Waiting / Needs attention badge), press Check again, then create the inbox. The create button stays disabled until the domain is verified and both the receiving and the sending-proof records are valid; the API refuses independently. The page also lists the DMARC record Mailgun does not return.

The branded address is its own record. A fourth group carries one CNAME, inbox → inbox.coreswiftcrm.com, which makes inbox.<their-domain> open the mail client on the customer's own name. It must be Proxied (orange cloud) at their Cloudflare — the reverse of every mail record, which must be grey — because their certificate carries the padlock. The server MEASURES the name (it asks it for the mail client) and answers active, waiting or attention; attention means the name resolves but serves something else, which in practice is Cloudflare's SSL/TLS mode set to Full (strict) refusing our origin certificate. The Shared Inbox tab's LOG IN button opens the branded name when it is active and inbox.coreswiftcrm.com while it is not, so the button is never a dead link.

Nothing is charged and no mailbox exists until verification passes. The 30-day trial starts at the customer's FIRST VERIFIED MAILBOX, not at signup; a later inbox on the same account inherits that window rather than restarting it. When the plan's inbox allowance is used up, the refusal names the plan that unlocks more and its price (read from the plan registry, so it can never promise an allowance the plan does not sell) and says plainly that nothing was charged and no mail was deleted.

All the numbers are registry data on the private_email module, editable in this console without a redeploy: email_mailboxes (Free 1), email_domains (Free 1), email_sending (Free off — the trial grants it per mailbox), email_trial_days (30), email_outbound_per_day (200, a fair-use ceiling that protects the sending domain) and email_storage_mb (free 2048 MB, then 5120 / 10240 / 51200 / 102400 / 256000 MB up the ladder).

The mailbox carries its own state: trial → receive_only → paid. A sweep runs hourly at :07 and once at every boot, idempotent, and writes exactly one audit_logs row per transition (action mailbox.trial_expired). It never deletes a message or a mailbox. Because the send path also reads the plan and the trial deadline live, moving a account onto a paid plan restores sending on the very next request, and that same request settles the mailbox's stored state to paid. The sweep never expires a mailbox whose plan sells sending, so a paying customer never collects a “trial expired” audit row.

The Inbox plan exists with one mailbox, one domain, unlimited history and sending on — and no CRM: every other module is an explicit false row for it, so a CRM route answers the normal plan refusal. It ships inactive until a working payment page is pasted onto it, so no customer can reach a button that cannot take money; the plan screen still shows it, with its annual price and a Request path.

Upgrading a account off Inbox ends the Inbox line in the same action. Every account holds exactly ONE open plan line: the plan write closes the old line and opens the new one in a single statement, and the database refuses a second open line for the same account, so a customer can never be billed for Inbox and a CRM plan at once. Plans & Billing now opens with Your bill, which states the single amount due, says there is one subscription, names the line that ended when the account last moved, and gives the date it ended. Once the Inbox row is reactivated, moving a account back down to Inbox puts it back on Inbox again and leaves its mailbox and every message untouched; while it is inactive the plan writer refuses it as not on sale, so no account can move onto it. The ledger is the append-only plan_lines table — a closed line keeps its own price, cycle and dates — and the trigger on tenant_plans is its only writer, so even a hand-run plan correction is recorded.

The three record groups, so you can name them on a call. MX (two records, mxa.mailgun.org and mxb.mailgun.org) is where mail is delivered — without it nothing arrives. How a customer gets sending back. Keep inbox buys the mailbox alone; Upgrade CRM buys the platform. Both are a plan move, so sending works on the very next request — there is no job to wait for, and no message is lost or re-sent.

Sending and receiving are separate choices (Mailgun is no longer the only receiver)

A customer can send through one service and receive through another. The inbox setup page asks two independent questions, and the server stores them in two columns: provider_type answers how the domain SENDS (mailgun over Mailgun's API, or smtp for Amazon SES / SendGrid / Postmark / Google Account / any SMTP server) and inbound_provider answers how it RECEIVES (mailgun, sendgrid, or none for a sending-only domain). Before this, one column answered both, so a customer who wanted to keep their own sender was told to move their inbound mail.

The combinations, and what each one means. Mailgun+Mailgun is the original setup. The automation lane is a separate subdomain. Automated mail — auto-responders, email sequences and the send_email rule action — never leaves from a account’s main domain. It is sent from mg.<domain>, a subdomain derived automatically from the account’s verified domain (no operator or customer setup step), with h:Reply-To set to the account’s own inbox address so replies land in the private inbox. The queue marks such messages outbound_messages.automation_domain, and the worker resolves that lane’s transport from the account’s own Mailgun credential — never the main-domain identity. This split is what keeps a complaint about an automated blast from damaging the domain real conversations arrive on.

The SendGrid receiver

POST /api/v1/webhooks/sendgrid/inbound/<token> — the token is per domain (private_email_domains.inbound_token, 32 hex characters, minted on write and shown only on that domain's records response as inbound_parse_url). SendGrid Inbound Parse signs nothing: there is no HMAC and no shared-secret header, so the unguessable URL is the credential — the same shape as /api/webhook/<token>/<action>. Three refusals matter on a support call: an unknown token is 401 and writes nothing; a domain whose receiving provider is not SendGrid is refused with a sentence naming the receiver it does use; and a delivery whose recipient belongs to a different domain than the token's is answered received: false (a valid token is not a key into another account's inbox).

Verifying a SendGrid domain is DNS, not an API. SendGrid publishes no endpoint that says "this domain is mine", so Check again and the records page ask DNS-over-HTTPS whether the domain's MX names mx.sendgrid.net. dig is not installed on this box; the check runs over DoH deliberately. Promotion only, exactly like the Mailgun arm: one ambiguous read never demotes a working domain.

What the setup page shows for a SendGrid receiver. Two rows are ours: the MX (mx.sendgrid.net, priority 10) and the Inbound Parse URL with a copy button. Sending records are NOT invented — for an SMTP sender the page carries one row saying where they come from (the sending service), and for a Mailgun sender it shows Mailgun's own sending records. The DMARC row and the branded inbox.<domain> CNAME appear in both shapes.

Amazon SES inbound is deliberately NOT offered. It arrives as an SNS notification pointing at an S3 object, so it needs its own signature verification (SNS certificate fetch and validation) plus a raw-message fetch — a bigger job than the SendGrid shape — and no customer is blocked without it: SES sending already works over SMTP, and receiving is covered by Mailgun and SendGrid. No dropdown entry claims it.

Switching receiving later is PATCH /api/private-email/domains/:id with receiving_provider. It never touches sending, never deletes a message, and mints the inbound token when SendGrid is chosen and none exists. The console offers it under the domain on the setup page.

Catch-all is part of the plan, not a domain setting

What it does. With catch-all on, the inbound receiver accepts a message for any address on that domain, including one no mailbox row exists for, and stores it in the account’s Everything else (MISC) bucket. With it off — and with it on under a plan that does not sell it — the delivery is refused, byte-identically to a domain that never had it, so the sender gets a bounce and the account sees nothing.

Who it is sold to. On this install plans.features.catch_all is true for Pro, Professional, Enterprise and Agency, and absent on Free, Inbox and Starter — but Pro is not on sale (plans.is_active = false, deactivated 2026-11-10) and Inbox is an add-on, not a plan on the ladder, so the plans a customer can actually buy that include catch-all are Professional, Enterprise and Agency. The switch is per domain (private_email_domains.catch_all_enabled), but the plan is asked at delivery time: the switch is a preference and the plan is the entitlement. A account downgraded off a plan that sells it keeps the switch remembered and receives nothing on it until it comes back up, and the console paints off — not on your plan with a Clear button rather than showing a switch that lies.

Reading it per tenant. GET /api/v1/private-email/admin/limits/:tenant_id answers sells_catch_all (the entitlement), catch_all_domains_enabled (how many domains carry the remembered switch) and catch_all_domains_off_plan (how many are being refused right now). A non-zero third figure after a downgrade is ordinary residue, not a fault — and it is the exact answer to “I turned catch-all on and mail still bounces”.

What it is not. It creates no mailbox: a catch-all arrival has no address to sign into and starts no trial. It also never becomes a support ticket by itself — a person files it, or a rule does.

The refusal sentence is read from the plan catalogue. Pressing Enable catch-all on a plan that does not sell it answers with the cheapest active plan that does sell it, and that plan’s price — today it names the Professional plan and appends the price the catalogue holds for that plan. Nothing in the sentence is typed by hand: feature_gate::catch_all_refusal reads plans (active only, cheapest first) joined to the private_email module and the same features.catch_all flag the delivery gate reads. That coupling is the point: re-pricing a tier, giving catch-all to a cheaper plan or re-activating Pro changes the answer with no redeploy and no guide edit. The console prints the server’s sentence verbatim, and the same clause builds the off — not on your plan hint on the domain list, so the refusal and the hint cannot disagree.

Mailbox storage: the quota, the reminder ledger, and the retention backstop

Storage, not a clock, is what bounds a mailbox (B206, David 2026-11-11 revised). Every account has an allowance from the private_email module registry key email_storage_mb. This install ships: free 2048 MB (2 GB), inbox 5120 MB (5 GB), starter 10240 MB (10 GB), professional 51200 MB (50 GB), enterprise 102400 MB (100 GB), agency 256000 MB (250 GB). The ladder is monotonic with price, so an upgrade always buys more storage; every plan now carries an explicit number (the paid plans used to be NULL = uncapped, which meant their meter could never warn). A per-account tenant_plans.feature_overrides entry ({"email_storage_mb": {"enabled": true, "limit_value": 2048}}) overrides one account without a redeploy.

What the figure counts: every stored message in private_email_messages.size_bytes (inbound and outbound), plus tenant_logos.bytes and user_avatars.bytes. One function (private_email::storage::usage) computes it, and the meter, the in-app banner, the reminder email and the 100% refusal all read it, so the number a customer is shown and the number that refuses a file cannot disagree. GET /api/private-email/messages/counts answers it as storage{used_bytes, quota_bytes, percent, level, used_human, quota_human, banner{...}} plus retention{...}.

The three rungs and the reminder ledger. At 50%, 75% and 99% the mail screen shows a banner that stays until space is freed, and the account owner is emailed once per rung per month. The dedupe is the table private_email_storage_notices, unique on (tenant_id, threshold_pct, period) where period is the UTC month: the row is claimed (INSERT .. ON CONFLICT DO NOTHING RETURNING id) BEFORE the mail is queued, so a provider retry, a burst of inbound deliveries, and the ten-minute sweep cannot send a second message for the same rung in the same month. The email is rendered by the storage_warning template type (inline plain-text body, editable per account through the template registry); it states the actual figures, the action, the retention backstop and the two links. A queue failure releases the claim so a later pass retries instead of silently skipping the month. The rungs are evaluated on every counts read (a customer who opens their mail is told immediately) and by a sweep every ten minutes at :13 for owners who never open it.

At 100% (and above) nothing is refused except a new file. Inbound mail is still stored (the quota never touches the receive path), sending still works, and no row is deleted to make room. A new logo or profile picture is refused with 402 and a sentence naming both figures and both ways out: delete/archive mail (Trash and Spam count until emptied), or upgrade. The refusal is one function (storage::enforce_new_file_room) called by the two upload doors. A full mailbox therefore never loses the owner business a bounce would.

Time-based retention is a far backstop, not the rule. tenant_email_limits.retention_days defaults to 3650 (ten years) since migration 142, and every existing row shorter than that was raised, so this deploy deletes no customer mail on a clock. The daily 03:00 sweep removes rows older than the window from private_email_messages, outbound_messages and email events; its answer reports inbox_messages_deleted separately. The admin retention route keeps the 30..3650 control and now reports the backstop when an account has no explicit row. The mail screen states the window that applies, with the date the oldest stored message would reach it, so nothing is ever removed silently.

Logo and signature on a customer's mail

Each account has one email logo and one default signature, both set by the customer on Email Branding in the tenant console; the per-mailbox override is in the mail client's Signature button, not in this console. This is unchanged by the operator: there is no platform-level switch that turns a customer's signature on or off. The operator console's Email Branding tab carries the same five fields for the account it is acting for (a Company signature card with its own Save signature), so branding a account on its behalf reaches the same single writer, PUT /api/private-email/signature/account.

What the server does

  • The logo is resized once, at upload (POST /api/account/branding/logo): decoded with the image crate, fitted inside 440 x 176 px (2x the 220 x 88 px it is drawn at, so it stays sharp on retina screens), never upscaled, and re-encoded as PNG — Outlook does not render WebP, so the format is forced rather than trusting the upload. The pixel size is stored in tenant_logos.width_px/height_px so the HTML can carry width/height attributes (Outlook sizes an image from the attributes before it loads). The response reports source_bytes, bytes, width_px, height_px; the storage quota is charged the RESIZED size.
  • The signature is data, not a template: tenant_email_signatures holds the account default (name / title / company / phone / line), and private_email_boxes holds each address's signature_mode (inherit | custom | off) plus its own five fields. custom falls back to the account value per field; off prints nothing, including the legacy free-text private_email_boxes.signature column, which is still appended when it is set on an address that is not off.
  • The block is built in send_handler::deliver — the one place mail leaves an account — so compose, reply, reply-all and forward all get it and no second sender can skip it. include_signature: false on POST /api/private-email/send or …/messages/:id/reply drops it for one message (absent means yes).
  • The logo is an inline MIME part, not a link. The HTML points at cid:coreswift-logo.png and the bytes travel in the message (Mailgun: hand-built multipart with the part named inline and the Content-ID derived from the filename; SMTP: multipart/alternative whose HTML arm is multipart/related with Content-ID). That is why deleting or replacing a logo cannot break already-sent mail, and why the logo draws even where remote images are blocked.
  • The typed body is escaped and its line breaks preserved before the block is appended, and every message now carries a plain-text alternative (text on Mailgun, a text/plain part over SMTP). Before this the typed plain text was sent AS the html part.

Reading it back / proving it

  • GET /api/private-email/signature?mailbox=info@example.com — what Compose shows that address: resolved fields, mode, and the server-rendered html (public logo URL, not cid:).
  • GET /api/private-email/signature/account — the account default plus its rendered preview.
  • PUT /api/private-email/signature — one address's mode and five fields. PUT /api/private-email/signature/account — the account default, and its ONLY writer.
  • All four are on the private-email router, i.e. behind the same sign-in as every sibling route; none is on an allowlist.

If a customer reports a missing logo, check in this order: select content_type, width_px, height_px, octet_length(bytes) from tenant_logos where tenant_id=… (the row exists), select settings->'email_branding'->>'logo_url' from tenants where id=… (the pointer the mailer reads), then the address's signature_mode — an address set to off sends nothing at all, logo included, by design.

Email compliance — the numbers, the opt-outs, and the three lanes

Every message this app sends on a account's behalf now leaves evidence, and every account can see its own. Nothing here is estimated by the app: the delivery, bounce and complaint numbers come from the provider's own reports, arriving on a signed webhook and matched back to the account that sent the message.

What the Mail compliance tab answers

  • Delivery rate — accepted and delivered, not merely "we handed it over".
  • Bounce rate — the share of a list that no longer exists. Above roughly 5% it is a list problem; the account's bulk lane pauses itself and the account is told to clean the list.
  • Complaint rate — spam reports. The mailbox providers' ceiling is 0.30%; crossing it is how a sending domain stops working for everyone who uses it.

Until the first report arrives the tab says so instead of showing zeros, and the daily allowance is counted from the send log, never from a counter that can drift.

What is never stoppable, on purpose

Receipts, password resets, security notices and the operator's own support-request alert are transactional: a customer's "unsubscribe from everything" cannot silence them. That classification was wrong once — the operator alert was a stoppable class, so an owner who unsubscribed stopped being told somebody had asked for help. If you ever add a new message type, ask which of these it is before it ships: can the recipient's preference be allowed to lose this message? If the answer is no, it is transactional.

The do-not-mail list belongs to the account, never to the platform

One account's opt-out must never silence another account's mail to the same person, so suppression is stored per account. When a account asks why an address is blocked, read their list — never copy a block from another account "to be safe", and never lift one that came from a hard bounce or a complaint: those are harm control, not preference.

Do not mail — the screen (operator console, Settings)

The operator console now carries Do not mail under Settings, beside Email Branding: the same account-scoped list the customer console's Mail compliance tab shows. It answers, in one screen, how many addresses are on the list, how many were added in the last 30 days, and the month's hard bounces and spam complaints — the two that add an address by themselves when the provider reports them. Four controls, each doing exactly one thing: Add to the list records an address that asked by phone or by hand (recorded as manual, so an operator's entry can never be mistaken for a bounce or a complaint), Allow again lifts a row so future mail reaches that address, and the two downloads give the do-not-mail list as a CSV, or every contact address in the workspace one per line for pasting into a checker. Lifting an address refuses a row that belongs to another account (it answers "no such suppression in this account") and never recalls anything already sent. Every row prints where it came from — console for a hand-added one — and the list is read and written under the signed-in account, so nothing here can see or lift another workspace's block. An API client that sends any other reason or mail_class is refused with a 400 naming the allowed values — the five reasons above, and all / bulk / notification / transactional for the scope — so a typo is never recorded as if it were a real preference.

The opt-out page and its wording

The page lists the campaigns that address is actually in, each with its own tick box, plus one stop-everything choice. A tick on one campaign stops only that campaign. The wording (title, explanation, stop-everything label, button, and the two confirmation lines) is per account and edited from the Mail compliance tab by an owner or an admin; clearing a line restores the platform default rather than leaving a blank page.

Three lanes, one domain

A account adds a domain once and then chooses its jobs. Inbox carries human replies; automation (mg.) carries campaigns so a bad blast cannot damage the name replies come from; calendar (booking.) serves public booking pages. Each lane is offered only when its own records verify — a waiting lane reads "waiting on records" with the exact DNS rows to add, and a host must sit under a domain the account has already added.

While a account sends on the platform's shared identity it shares that reputation with every other account, so the shared identity carries a small daily allowance (100/day by default) and an owned domain carries a large one (2,000/day). Transactional mail is never capped: a cap there is an outage.

When a customer says "my mail isn't arriving"

  1. Their complaint and bounce rates — a paused bulk lane explains the silence and names the fix.
  2. Whether the address is on their do-not-mail list, and why (unsubscribed / hard bounce / complaint).
  3. Whether the lane is verified, or still waiting on DNS.
  4. Whether they are on the shared identity allowance and have spent it.

Each of those four answers is visible in the console, and the send log records every attempt with the reason it was refused, so the answer is read rather than guessed.

Inbound mail: which credential is authenticating a delivery

Two credentials can authenticate a Mailgun inbound delivery, and the log says which one was used:

  • "authenticated by the platform webhook token" — the domain has no signing key, so the forward URL's platform token authenticated it. This is the default state and it receives fine. It is a shared credential for the fleet, not per account.
  • signature — the domain's own signing key validated the delivery. Stronger and per account.

The key is 32 hexadecimal characters (Mailgun → Settings → API Security → HTTP webhook signing key, press Show), account-wide, not per domain. A 50-character value with dashes is the sending API key and is now refused at the door, because accepting it looked healthy in the panel while refusing every delivery — the failure mode that reads to a customer as "the inbox is broken".

If a wrong key is ever stored, use Remove key: with no key the receiver authenticates on the platform token and mail flows, whereas a wrong key refuses everything. Removing is a repair, not a downgrade.

Inbound mail names the customer from the From header, not the envelope sender: a relaying provider rewrites the envelope to bounce+<hash>@<its domain>, and reading that as the sender mislabels the message and stops a ticket from being opened for it.
